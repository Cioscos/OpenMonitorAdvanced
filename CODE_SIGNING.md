# Code signing policy

OpenMonitor Advanced is a free, open-source hardware monitor for Windows (GPL-3.0-or-later). This
page describes how its Windows binaries are, or will be, signed.

## Status

Code signing is **planned, not active**. The application to the
[SignPath Foundation](https://signpath.org/) has not been submitted yet, so no release is signed
and Windows SmartScreen may warn when you run the installer (see the README). Until the
Foundation approves the project and the first signed release is published, this page states the
policy that will apply; it does not claim that any release is signed.

When signing is active, this page will carry the attribution required by the Foundation and the
README will point to it.

## Roles

| Role | Who |
|---|---|
| Committers and reviewers | [@Cioscos](https://github.com/Cioscos), the owner of the repository |
| Approvers | [@Cioscos](https://github.com/Cioscos) |

Every signing request is approved by hand on SignPath by the approver. Two-factor authentication is
required on GitHub and on SignPath for every role.

## What is signed

Each release is built from a version tag by the GitHub Actions workflow
[`.github/workflows/release.yml`](.github/workflows/release.yml) on a GitHub-hosted runner. Once
signing is active, these files carry the signature:

- the installer (`OpenMonitor Advanced_X.Y.Z_x64-setup.exe`);
- `oma-app.exe`, the application;
- `oma-service.exe`, the optional sensor service;
- `oma-overlay.exe`, the in-game overlay window the application starts, installed next to it
  (from version 0.5.0), under the same policy as the application;
- `oma-load.exe`, the process that runs the stress tests, which the application starts, installed
  next to it, under the same policy as the application;
- `uninstall.exe`, the uninstaller generated by NSIS, so that the Windows confirmation prompt of
  the uninstallation also shows the publisher.

The signed files carry the product name "OpenMonitor Advanced" and the release version. From
version 0.3.0, each release also ships `SHA256SUMS.txt` and a GitHub build provenance attestation (see the README,
"Verify your download").

## What is not signed

Only our own code is signed. Third-party files are never submitted to SignPath and keep the
signature, or the lack of one, of their authors:

- `PawnIO_setup.exe`, the installer of the [PawnIO](https://pawnio.eu/) driver, bundled
  unchanged and checked against a pinned SHA-256 at build time;
- `PresentMon-2.6.0-x64.exe`, Intel's [PresentMon](https://github.com/GameTechDev/PresentMon)
  console from the official v2.6.0 release, which we redistribute unchanged next to the service
  (`service\presentmon\`). It is signed by Intel Corporation, not by us: the build accepts it
  only with the pinned SHA-256 (`app/src-tauri/nsis/presentmon.sha256`) and a valid Authenticode
  signature by Intel, the release verification checks both again in the setup, and the service
  checks the hash before every start;
- the NSIS plugin DLLs (`nsExec.dll`, `NSISdl.dll`, `System.dll`, ...), which stay unsigned.

## How to verify a signature

In PowerShell:

```powershell
Get-AuthenticodeSignature -FilePath .\OpenMonitor.Advanced_X.Y.Z_x64-setup.exe |
  Format-List Status, StatusMessage, SignerCertificate, TimeStamperCertificate
```

`Status` must be `Valid` and the signer must be "SignPath Foundation". The same command works for
`oma-app.exe`, `oma-overlay.exe`, `oma-load.exe` and `service\oma-service.exe` in the installation folder (by default
`C:\Program Files\OpenMonitor Advanced`) and for `uninstall.exe`. For the installer you can also
check the checksum and the build attestation as described in the README.

## Privacy

This section describes what we verified in the project's own code, installer and bundled
components. Where a third-party component has its own behavior, we link to its policy instead of
describing it.

- **The application (`oma-app.exe`), the overlay (`oma-overlay.exe`), the load generator (`oma-load.exe`) and the service
  (`oma-service.exe`) send no data over the network, except the optional update check below.** There is no telemetry. The only HTTP client
  is the update check of the application (WinHTTP, in `crates/oma-win/src/http.rs`); the service
  has none. The web interface may talk only to the local Tauri bridge (its content security policy
  allows `connect-src ipc: http://ipc.localhost`). The app and the service communicate with each
  other over a local named pipe; the app and the overlay over another one, with a random name,
  that only the current user can open. The sensor library the service uses, LibreHardwareMonitorLib
  0.9.6, references no HTTP or socket types, only the local network adapter list
  (`System.Net.NetworkInformation`).
- **Settings, history and the optional CSV log stay on your PC**, in
  `%APPDATA%\OpenMonitorAdvanced` and in the folder you pick for the log. Nothing is uploaded.
- **The interface is rendered by Microsoft Edge WebView2**, which is a Microsoft component with its
  own privacy behavior, outside our control: see the
  [Microsoft Privacy Statement](https://privacy.microsoft.com/privacystatement) and the
  [WebView2 documentation](https://learn.microsoft.com/en-us/microsoft-edge/webview2/).
- **The installer downloads Microsoft's WebView2 bootstrapper only if WebView2 is missing.** We use
  the Tauri default (`downloadBootstrapper`): when no WebView2 runtime is registered, the installer
  fetches the Microsoft bootstrapper from `go.microsoft.com` and runs it. Windows 11 ships the
  runtime, so there the download normally does not happen. The installer downloads nothing else.
- **PawnIO is bundled, not downloaded.** `PawnIO_setup.exe` is inside our installer. It is installed
  only if you keep the *Advanced sensors* component selected. For the driver's own policies see
  [pawnio.eu](https://pawnio.eu/).
- **PresentMon is bundled, not downloaded.** `PresentMon-2.6.0-x64.exe` is inside our installer
  and installed with the *Advanced sensors* component. The service starts it only while the app
  asks for frame metrics (the in-game overlay is on) and reads its output over a local pipe; no frame data is written to disk
  (only PresentMon's error output goes, truncated, to the service log) and the frame data go only
  to the app. Measuring PC latency, which is never on unless you ask for it,
  makes games with Reflex send themselves a ping (a window message or F13–F15 key presses): see
  the README, "In-game overlay". For PresentMon's own documentation see its
  [repository](https://github.com/GameTechDev/PresentMon).

**Update check (optional).** The app can check whether a newer release exists. It does so only
when you press *Check now* in Settings › About, or once a day if you turn on *Check automatically*
(off by default). The check is a single HTTPS request to `api.github.com` for the latest release of
this repository; it sends your IP address, as any connection does, and a User-Agent with the app
version. No identifiers, no settings and no sensor data are sent. GitHub's own policy applies to
that request:
[GitHub Privacy Statement](https://docs.github.com/site-policy/privacy-policies/github-general-privacy-statement).
The app never downloads or installs anything: it shows a link to the release page. The service
never uses the network.

**Sensor report.** *Export sensor report* in Settings › About writes an anonymous JSON file to a
folder you choose. Nothing is sent: you attach it to an issue yourself if you want to.
